# 产品介绍页

围绕“用户一眼理解产品是什么、为什么需要、如何获得价值”组织页面。先理解产品、用户和真实功能，再提炼价值、设计证据和视觉；不要把功能堆砌、装饰或猜测当成产品解释。

## 使用配套资料

- 开始新页面、制定方案或交付验收时，读取 [制作与验收工作表](references/work-templates.md)，按任务规模选用需求摘要、页面表、动效脚本和验收记录。
- 需要学习价值提炼、真实操作展示、独立文档证明或循环动画时，读取 [ChatNote 案例](references/chatnote-case.md)。只迁移方法，重新核实目标产品事实。
- 制作网站时同时遵循可用的网站制作与交付工作流；本 Skill 负责内容、设计和验收，不替代网站或视频工具的执行要求。

## 1. 理解产品并界定任务

- 读取用户提供的产品、截图、源码、真实界面、现有网站及已确认文案；区分当前版本已实现、计划功能和不确定内容。涉及宣传事实和下载包时核实版本及行为，发现差异直接说明，不夸大或自行补全。
- 明确目标受众、使用场景、痛点、核心价值、关键转化及限制；写出一句可核对的理解：用户在什么情境遇到什么困难，产品通过什么动作解决，得到什么价值。具体问题可来自对话和素材，缺少关键事实才询问。
- 识别用户是在要求方案、评价还是直接执行。明确“先给方案、确认后执行”时停止在方案，不预先改动；方案获确认后执行。否则在可判断范围内自主完成，不将常规选择变成确认流程。
- 既有项目先记录修改范围和用户已认可的内容；只改指定区域，保留其他文案、素材、尺寸、交互和动效。明确区分用户对产品界面不可改动的要求与视觉包装可调整的部分。

### 设置必要的检查点

新页面先形成简短需求摘要和页面策划表，再制作首屏与一个具有代表性的核心模块来验证方向；方向明确后扩展全页。用户已明确风格、结构或要求直接完成时自主推进，不重复索取确认。若用户要求先给方案，只交付方案；方案包含具体文案、模块顺序、画面内容与验收方式，而非抽象风格词。

将“高级、简约、有生机”等要求转成具体可检查的设计选择，例如标题层级、UI 可读比例、视觉焦点、对齐与动效节奏。参考图先提取用户认可的具体手法，避免照搬整张图或误改产品身份。

## 2. 组织价值与内容

- 先给出受众痛点、核心价值和三个左右互不重复的卖点（数量随产品调整），逐项对应真实功能及可验证的画面证据。用“核心价值 → 功能名称 → 简短价值 → 功能描述 → 画面”建立层级。
- 首屏主标题用简短自然语言表达具体用途和价值；辅助文案说明产品是什么、在哪个场景使用。避免只有口号、空泛效率词、重复标题和无关参数。允许用户确认后再实施，如其要求分阶段。
- 功能标题先让读者知道功能是什么，再用简短后半句表达价值；描述说明触发、关键能力和用户获得的结果。少字但不牺牲准确性，不添加未经确认的功能、效果或版本承诺。
- 根据功能关系选择布局：相互独立的功能可并列；共享同一场景或重复界面的功能合并展示；需要解释状态变化的功能使用动效。保持核心模块清晰、页面紧凑但界面可读，不用缩小产品内容来压缩页面。

## 3. 设计产品图与动效

先为每张图写一句“观众应立即理解什么”，再确定场景、操作、变化或结果。尽量让一张图承担一个重点：保留真实 UI 的关键按钮、图标、比例、文案和界面关系，裁切与弱化非重点内容，保证必要部分完整、清晰。用轻量高亮、颜色或短标签突出动作和结果；避免无意义大字、堆叠卡片、虚构界面和遮挡重点。

- 要证明操作结果时展示动作发生的真实环境和结果，例如触发按钮、对应目标区域及添加后的状态；要证明同步或关联时展示同名对象和对应状态，而不只靠箭头和说明。
- 参考竞品可借鉴布局、信息层次和展示手法，不能改变原产品的图标、人物、功能或实际交互。用户提供的 UI 和品牌素材优先；不能确认时标示不确定或先索取必要资料。
- 静态图适合呈现明确状态或关系；切换、选择、添加、保存前后等需要时间顺序理解的动作使用循环动效。制作前定义起点、动作、目标、变化、停留和循环接缝，动作结束后维持完成态再自然循环；不闪白、不重复写入、不凭空更换状态。
- 动效检查鼠标落点和点击时序、选区准确性、界面宽高、裁切、速度、状态衔接和全周期。相邻动效应协调；已通过的素材不要因其他调整被替换。实际浏览器验证播放，包括用户环境可能影响动效的设置；不能验证时如实说明。
- 优先复用当前项目的技术栈和真实素材。用户指定视频、动效或网站工具时遵循相应工作流；不要把复杂精确 UI 交给图像生成臆造。

## 4. 视觉与实现

基于品牌与用户提供的参考图选择样式；用留白、网格、对齐、排版、图像比例和强调建立层次，简洁不等于空白朴素。控制装饰、色彩和小字密度；用户已认可的内容不改。配图不抢走产品本身的注意力。检查宽屏和手机阅读、标题和下文间距、文本与图片对齐、图片完整性。

检查真实下载链接及安装包版本、文案与当前功能是否一致、外部链接与资源路径是否可用。按项目自身的发布与权限规则完成交付；不要擅自更改访问范围。只报告已实际验证的行为。

### 处理修改反馈

先定位问题属于价值文案、信息结构、布局视觉、素材真实性还是操作时序，再作相应范围修改。“太单调”需要增强视觉重点、构图或状态变化，不默认堆装饰；“太长”先改善模块组织与阅读节奏，不擅自删掉必要内容。维护简短的已确认事项、待解决项与本次修改范围，防止后续改动推翻前面已通过的结果。

## 5. 交付前验收

按用户视角检查：
1. 首屏是否不用长篇解释即可理解产品用途与价值；每个卖点是否有具体功能与证据支持。
2. 画面是否能看懂场景、动作和结果；关键 UI 是否真实、完整、不被遮挡，文字是否过多或不必要。
3. 动图是否从第一帧到循环接缝均正确，鼠标、速度与状态一致；浏览器与移动端是否可正常显示。
4. 用户指定范围以外是否发生变化；已确认的文案、图形和动效是否保留。
5. 名称、功能、版本、安装说明及下载包是否一致，链接和实际操作是否可验证；明确未验证项与已知不一致。

实际验证主要链接、交互和桌面/移动端布局；有动画时观察至少两个完整循环，并检查减少动态效果设置下的可理解性。发现问题先修复再交付，无法验证的项目明确标记。

向用户概括变更、可查看的结果、必要的验证与限制。优先直接给可访问的网页或文件；当用户要求先看方案时，只交付可审阅的结构、文案和画面方案，等待其确认。
